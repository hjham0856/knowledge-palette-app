# 구현 중 결정한 사항

기획 문서가 에이전트에게 위임했거나 아직 정하지 않은 세부 사항을 Phase 3~6 구현 과정에서 다음과 같이 정했다. 각 항목은 선택과 그 이유를 함께 적는다. 이미 확정된 Phase 1·2 결정은 `knowledge-palette-architecture.md`의 "Phase 1/2 결정 사항"에 있다.

## 작업 방식

- **코드 작성은 Codex(`codex exec`, 모델 `gpt-6.1-sol`, 추론 강도 medium)에 위임한다.** Claude는 계획, 작업 조율, 코드 검토, 검증, Git 작업, 문서 기록을 맡는다. 이유: 사용자가 이렇게 역할을 나누라고 지시했다.
- **세션은 구현 단계마다 새로 열고, 같은 단계의 검토 수정만 `codex exec resume`으로 이어간다.** 이유: 같은 기능의 맥락은 유지하되, 다른 단계의 맥락이 섞여 범위를 넘는 구현이 생기지 않게 하기 위해서다.
- **Knowledge Delta의 결정 값은 `NONE`으로 쓴다.** 사용자가 MVP 범위 문서에서 `NOOP`을 `NONE`으로 바꿨고, 후보 유형에서 "프로젝트 판단/결정"을 뺐다. 이 수정을 확정 규칙으로 보고 다른 문서의 표기도 맞췄다.

## 디자인

- **"Tally 디자인"은 Hallmark 공개 예제 https://www.usehallmark.com/examples/tally/ 의 디자인 언어로 해석했다.** Hallmark 카탈로그에는 Tally라는 테마가 없고, 이 예제는 `theme: Pastel · genre: modern-minimal · nav: N5 Floating pill`로 표기되어 있다. 다음 요소를 앱 UI 토큰으로 옮긴다.
  - 차가운 파스텔 종이색(paper)과 짙은 남색 잉크(ink)
  - 인디고 액센트와 아껴 쓰는 라임 보조색
  - Geist / Geist Mono 폰트
  - 6·12·20·28px과 pill 반경
  - 4pt 간격
  - hairline 경계선
- **Instrument Serif 이탤릭 강조는 가져오지 않는다.** 원본 예제는 제목에 이탤릭 세리프 강조를 쓰지만, Hallmark 규칙은 제목 이탤릭을 금지한다. 또 이 앱은 랜딩 페이지가 아니라 작업 도구라 장식보다 읽기가 우선이다.
- **랜딩 페이지 구성 요소(마키 히어로, 가격표, 통계 줄)는 가져오지 않는다.** 지식 팔레트는 Main Canvas를 크게 쓰는 작업 화면이 원칙이다. 그래서 토큰, 플로팅 pill 내비게이션, mono eyebrow 라벨, 카드와 버튼 문법만 쓴다.

## LLM Provider

- **OpenAI 호환 Chat Completions API 하나만 지원한다.** 다음 환경 변수로 설정한다.
  - `KP_LLM_BASE_URL`, `KP_LLM_API_KEY`
  - `KP_CHAT_MODEL`
  - `KP_KNOWLEDGE_MODEL`: 비우면 Chat 모델을 함께 쓴다.

  이유: BYOK와 OpenAI 호환 API를 우선한다는 아키텍처 문서의 방향을 따랐다. 이 방식이면 Ollama, OpenAI, OpenRouter 같은 Provider를 코드 변경 없이 쓸 수 있다. 역할(Chat/Knowledge/Embedding)은 설정에서 나눈다.
- **실제 연결 검증은 로컬 Ollama의 `qwen3.5:4b-mlx`로 한다(사용자 지정).** 처음에는 한국어와 JSON 지시 수행을 기준으로 `qwen2.5:7b-instruct`를 골랐다. 이 모델로 Phase 3 첫 검증을 했지만, 응답에 중국어가 섞이고 사실 설명이 부정확했다. 이후 사용자가 실제로 쓰는 모델이 `qwen3.5:4b-mlx`라고 알려 와 그 모델로 바꿨다.
- **LLM 호출은 `LLMClient` 인터페이스 뒤에 둔다(사용자 요청).** 구현체는 OpenAI 호환 클라이언트 하나다. `KP_LLM_PROVIDER`로 구현체를 고르고, 역할(chat/knowledge)별 클라이언트는 진입점 한 곳에서 얻는다. 이유는 다음과 같다.
  - Provider를 바꾸거나 추가할 때 Chat과 Knowledge Update 코드를 고치지 않게 하기 위해서다.
  - 아키텍처 문서가 "특정 서비스에 Knowledge Engine을 종속시키지 않는다"고 했다.

  사용하지 않는 Provider 구현체는 미리 만들지 않는다.
- 자동 테스트는 외부 HTTP 경계만 대체(mock)한다. 실제 Provider 검증과 mock 검증은 작업 내역에 구분해 적는다.

## Phase 3 — Chat

- **응답은 SSE(Server-Sent Events) 스트리밍으로 보내고, 대화와 메시지는 PostgreSQL에 Workspace별로 저장한다.** 대화 원문을 저장하는 이유는 다음과 같다.
  - 기획 문서가 "초기에는 저장하는 편이 디버깅과 Undo에 유리하다"고 했다.
  - Phase 4가 대화 원문을 읽어 지식을 추출한다.
- **중단되거나 실패한 응답은 `interrupted`/`error` 상태로 저장하고 정상 완료(`complete`)와 구분한다.** 이렇게 해야 Knowledge Update가 미완성 응답을 지식으로 착각하지 않는다.
- **인용 라벨은 Note에 `[N1]`, Source 페이지에 `[S1]`을 쓴다.** 응답에 실제로 쓰였고 Context에 존재하는 라벨만 인용으로 저장한다. 모델이 지어낸 라벨이 실제 근거처럼 보이지 않게 하기 위해서다.
- **Context는 기존 Notes를 먼저, Sources는 사용자가 켰을 때만 넣는다.** 아키텍처 문서의 "기존 Notes → 필요한 Sources → 모델 자체 지식" 순서를 따른다. Source 검색을 매번 넣으면 Context가 원자료로 채워져, 사용자의 지식(Note)이 밀려나기 때문이다.
- **Chat 전체 화면이 기본이고, Split View는 사용자가 토글할 때만 연다.** 제품 문서의 "고정 3-pane 금지" 원칙을 따랐다.

### Phase 3 구현 세부 정책

- 정상 완료는 텍스트가 있고 `finish_reason=stop`과 `[DONE]`을 모두 받은 경우다. 빈 응답·형식 오류·HTTP 오류는 `error`, 연결 끊김·취소·그 외 종료 이유는 `interrupted`로 보존한다. Provider 오류 본문과 연결 예외 원문은 인증 정보가 포함될 수 있어 공개하지 않는다.
- 질문 전 Notes만 증분 재색인하고 개별 문서 실패도 Context 이벤트로 알린다. Sources는 사용자 수동 색인 정책을 유지하며, 현재 파일 상태와 일치하는 기존 인덱스만 검색한다. 오래된 검색 결과는 제외하며 검색이 불가능하면 해당 종류의 근거 없이 진행한다. 임의의 대체 검색은 하지 않는다.
- 참고 자료는 시스템 메시지에 넣고 현재 질문은 대화 이력에 한 번만 넣는다. 이전 응답은 `complete` 상태만 모델에 보낸다. DB·검색·임베딩은 threadpool에서 실행해 다른 요청을 막지 않는다.
- 모드 전환은 Chat과 Notes 인스턴스를 유지해 선택 Note·초안·스트림을 보존한다. 대화/Workspace 전환은 이전 스트림을 취소하고 화면 정리를 기다린다. 취소 직후 서버 저장이 끝나기 전의 부분 응답도 대화별로 잠시 보존한다.
- 모드와 Split 전환은 Note 저장을 먼저 기다리며 실패하면 전환하지 않는다. Note 로드·생성 잠금은 상위 내비게이션에도 전달한다. Split에서 인용을 누르면 같은 Note 편집기를 사용한다.
- `KP_CHAT_MODEL`은 필수다. `KP_KNOWLEDGE_MODEL`만 지정해서 Chat 모델로 대신 쓰지 않으며, Knowledge 모델을 비운 경우에만 Chat 모델을 공유한다. 비스트리밍 생성은 Phase 4에서 필요한 시점에 구현한다.

## Phase 4 — Knowledge Update

- **실행 시점은 세 가지다.**
  - 미처리 사용자 턴이 3개 이상 쌓이면, 응답이 끝난 뒤 백그라운드에서 자동 실행한다.
  - 다른 대화로 전환하거나 새 대화를 시작할 때 이전 대화에 대해 실행한다.
  - 수동 "지금 정리" 버튼으로 실행한다.

  이유:
  - 기획 문서는 "어느 정도 진행된 뒤 비동기 누적, 주제 전환·종료 시점에 통합"을 제안했다. 주제 전환을 자동으로 감지하려면 매 턴 LLM 판단이 필요해 비용과 불확실성이 크다. 그래서 대화 전환을 주제 전환의 근사치로 쓴다.
  - 브라우저 종료는 신호를 믿을 수 없어 쓰지 않는다. 그 대신 몇 턴마다 자동 실행해 앱을 닫아도 중요한 생각이 남게 한다(MVP 목표).
  - 매 턴 실행은 비용이 크고, 한 턴짜리 단편이 Note를 오염시키기 쉽다.
- **대화마다 처리 위치(watermark)를 저장해 같은 메시지를 두 번 처리하지 않는다. 같은 대화에는 동시에 한 번만 실행한다.** 중복 Note 생성을 막기 위해서다.
- **후보는 실행당 최대 5개, 유형은 생각/질문/통찰/일반 지식이다.** 저장 기준은 "다시 찾거나, 연결하거나, 발전시킬 가치"다. 모든 대화를 요약해 저장하면 Knowledge Base가 오염된다는 제품 정의를 따른 것이다.
- **CREATE/UPDATE/LINK의 대상은 앱이 검색한 관련 Note 후보 안에서만 허용한다.** 그 밖을 가리키면 NONE으로 처리한다. "쓰기 전에 검색한다"는 원칙을 지키고, LLM이 없는 파일이나 엉뚱한 파일을 가리키는 것을 막기 위해서다.
- **새 Note 파일명은 제목에서 파일시스템 금지 문자만 뺀 그대로 쓴다(공백·한글 유지).** 이름이 겹치면 ` 2`를 붙인다. wikilink가 파일명 기준이라, 사람이 읽기 좋은 파일명이 곧 읽기 좋은 링크가 된다. 기획 예시 `[[MMR과 지식 탐색]]`과도 맞는다.
- **UPDATE와 LINK는 문서 끝에 덧붙이기만 한다.** frontmatter는 `updated`만 바꾸고, 기존 문장의 삭제·수정·재구성은 하지 않는다. MVP의 "append 중심, 파괴적 재작성 금지" 규칙을 따른다.
- **태그는 자동으로 만들지 않는다.** 기획이 위임한 "Note tag 자동 생성 여부"에 대한 결정이다. 작은 모델이 만드는 태그는 일관성이 낮아 Base Lite 필터를 오히려 어지럽힌다. 태그는 사용자가 직접 관리한다.
- **실행 1회를 Knowledge Update 1건으로 묶어, 변경 전/후 내용과 해시를 기록한다.** 중간에 실패하면 이미 쓴 파일을 되돌린다. Phase 5의 "Update 전체 Undo"가 이 기록을 그대로 쓰고, 실패한 실행이 반쯤 반영된 상태로 남지 않게 하기 위해서다.
- **LLM 출력은 JSON으로 요청하고 pydantic으로 검증한다.** 실패하면 1회 재시도하고, 그래도 실패하면 파일을 바꾸지 않고 실패로 기록한다. 작은 로컬 모델은 형식을 자주 어기므로, 잘못된 출력으로 파일이 바뀌는 일을 막는다.

### Phase 4 구현 세부 정책

- 완료 턴은 complete 사용자 메시지 바로 뒤에 complete assistant 메시지가 있는 짝이다. 사용자 메시지는 질문 저장 시 이미 complete이므로, 응답 상태까지 확인해야 interrupted/error 턴을 제외할 수 있다.
- watermark는 applied 실행의 마지막 처리 메시지 id로만 이동한다. 빈 후보/NONE만 있는 정상 실행도 처리 완료로 보며, failed 실행은 같은 범위를 재시도할 수 있다. 참고 맥락은 직전 완료 메시지 4개(2턴)다.
- 요청은 실행을 등록한 뒤 즉시 running을 반환한다. 작업 task를 서버가 보존하며 LLM 호출은 응답 스트림과 분리한다. 조건 확인은 대화별 asyncio lock으로 직렬화하고 실제 실행 중에는 새 요청을 건너뛴다. DB conversation 행 잠금과 running 고유 인덱스도 중복 실행을 막는다.
- 모든 후보의 결정과 변경안을 메모리에 준비한 뒤 파일을 쓴다. 이후 후보는 같은 실행에서 CREATE한 Note도 연결할 수 있다. 같은 파일에 여러 변경이 있으면 최초 before와 최종 after를 한 change로 기록하며 CREATE/UPDATE의 의미를 보존한다.
- 카운트는 새 Note·보강 대상 파일의 수와 실제 추가한 연결의 수다. CREATE/UPDATE에 포함한 연결도 링크 수에 포함한다. NONE의 후보와 이유는 decisions에 남긴다.
- Note 원문은 bytes를 UTF-8로 해석해 줄바꿈을 정규화하지 않는다. updated의 값만 치환하며 인용 부호·주석·다른 키를 보존한다. updated가 없으면 키나 frontmatter를 새로 만들지 않는다.
- 검색 대상 밖의 target/links와 content 안의 허용되지 않은 wikilink는 NONE으로 기록한다. 링크 표기는 기존 Phase 1 규칙에 따라 중복 stem이면 notes 기준 상대 경로를 쓴다.
- 반영 트랜잭션에서 파생 인덱스 행을 stale로 기록한다. 반영 후 기존 indexer로 재색인하며, 실패한 변경 Note는 stale로 유지한다. DB가 완전히 불가능한 경우에는 failed 기록 자체도 저장할 수 없다는 물리적 한계가 있다.
- UI는 초기 대화 조회의 과거 변경을 새 변경으로 통지하지 않는다. 새 applied 결과만 열린 Note에 알리며 dirty 초안은 유지한다. 간단한 폴링은 2초 간격, 최대 130회이고 이후 수동 조회/재요청이 가능하다.
- 스키마 준비는 DB 주소별로 프로세스에서 한 번만 성공 실행한다. thread lock으로 초기 DDL을 직렬화해 자동 정리와 Chat 조회의 잠금 승격 deadlock을 방지한다.

## Phase 5 — History / Undo

- **Git이 아니라 앱 자체 History(DB 기록)를 쓴다.** 아키텍처 문서가 앱 자체 History를 우선하라고 했다. 또 Workspace가 Git 저장소가 아닐 수 있다.
- **Undo 전에 대상 파일의 현재 해시가 AI 변경 직후 해시와 같은지 확인한다. 하나라도 다르면 Undo 전체를 거부하고 충돌 파일을 보여준다.** 사용자가 이후에 직접 고친 내용을 AI 변경 되돌리기가 지워 버리는 것이 가장 나쁜 결과이기 때문이다. 부분 Undo는 "Update 전체를 되돌린다"는 규칙과 어긋난다.
- **Diff는 줄 단위로 비교하고 frontend의 `diff`(jsdiff) 패키지로 계산한다.** 변경 전후 원문이 이미 저장되어 있어 서버 계산이 필요 없다. 검증된 작은 라이브러리다.
- Redo는 MVP 범위 밖이다.

## Phase 6 — Knowledge Navigation

- **Local Graph는 1-hop(나가는 링크 + backlink)만 보여주고, 라이브러리 없이 SVG 방사형 배치로 그린다.** 문서가 Local Graph부터 시작하라고 했다. 1-hop 규모에서는 force 레이아웃 라이브러리가 필요 없다.
  - `GET /api/notes/graph?path=`는 Markdown 원본과 기존 Workspace 링크 해석·backlink 계산을 사용한다. 노드는 Note 경로로 식별하고 중심을 먼저 반환한다. 이웃 간 연결이나 2-hop은 포함하지 않는다.
  - 같은 이웃으로 향한 링크는 하나로 합친다. `source`/`target`은 실제 링크 방향이며, 양방향이면 중심→이웃을 대표 방향으로 두고 `bidirectional: true`, `direction: both`를 함께 반환한다. 자기 링크는 별도 이웃이나 연결선으로 표시하지 않는다.
  - missing·ambiguous는 `unresolved`에 대상·상태·후보 경로를 표시한다. 미해결 후보를 실제 연결로 보여주면 다른 Note를 임의 선택한 것처럼 보이므로 그래프 노드에 넣지 않는다.
  - Graph는 Notes의 선택 상태를 사용하고 기존 `selectNote`로 이동한다. 선택 함수가 저장 flush와 파일 로드를 마친 뒤에만 중심이 바뀐다. Notes로 돌아가면 같은 Note를 편집할 수 있다.
  - SVG는 글자 크기를 유지하며 연결 수에 따라 원을 넓힌다. 좁은 화면은 스크롤과 전체 경로 목록을 제공한다. 키보드 Enter/Space로도 노드를 선택할 수 있다. 실선·점선·굵은 선과 화살표·범례를 함께 사용한다.
- **Related Notes는 현재 Note 본문으로 기존 hybrid+MMR 검색을 재사용한다.** MMR의 "비슷하지만 다른 Note 발견"이 이 기능의 목적과 같다.
- **Base Lite는 쿼리 문법 없이 UI 컨트롤만 둔다(필터, 정렬, 그룹, 표/목록).** frontmatter 파싱은 backend가 하고 필터링은 클라이언트가 한다. 기획 문서가 "Dataview 전체 복제 금지"를 정했고, 개인 Workspace 규모에서는 클라이언트 처리로 충분하다.

### Phase 6-B Related Notes 구현 세부 정책

- 검색어는 YAML frontmatter를 제외한 본문 앞 1,200자다. 제목을 포함한 Markdown 본문을 그대로 사용하고 별도의 LLM 요약·검색어 재작성은 하지 않는다.
- 패널을 열거나 `다시 찾기`를 누를 때 저장 후 Notes만 증분 재색인한다. fingerprint가 동일하고 indexed인 Note는 기존 indexer가 건너뛴다.
- 자기 자신은 검색 후보 수집 단계에서 제외한다. `retrieval.search`의 선택 인자 `exclude_path`는 기본값이 빈 문자열이라 기존 검색 호출의 동작을 유지한다.
- 기존 MMR 순서를 따라 청크 결과를 Note 경로별로 한 번만 보여주고 최대 8개로 제한한다. 검색 후보 풀의 크기·가중치·임베딩 모델은 기존 값을 사용한다.
- 직접 연결은 기존 wikilink 해석 규칙을 따른다. 해석이 하나로 확정된 나가는 링크와 backlink를 각각 표시하며 모호한 링크를 임의로 연결하지 않는다.
- 일부 문서 재색인 실패는 전체 안내와 해당 결과의 `재색인 필요` 표시로 드러낸다. DB 연결·검색 모델 불일치·임베딩 검색 실패는 503과 `의미 검색 비활성`을 반환한다. 내부 예외 문자열은 연결 설정 노출을 피하기 위해 응답에 넣지 않는다.
- 본문을 바꾼 뒤에는 자동 검색을 반복하지 않고 갱신 안내를 표시한다. Note를 바꾸면 패널은 접힌 상태로 새로 시작하며 이전 요청의 응답은 버린다.
- Related Notes는 Notes 전체 화면에서 backlink 옆 접이식 영역으로 제공한다. Split의 compact 편집 화면에서는 기존 보조 영역 정책과 같이 숨긴다.

### Phase 6-C — Base Lite 세부 정책

- `GET /api/notes/frontmatter`는 DB 없이 `Workspace.note_files()`와 `safe_note_path()`로 Markdown을 읽는다. `path`는 notes/ 기준 상대 경로, `name`은 확장자 포함 파일명, `title`은 본문의 첫 H1(코드 블록 제외)이 없으면 파일명 stem이다.
- 파일 맨 위 `---`에서 `---` 또는 `...`까지를 PyYAML `safe_load`로 읽는다. 빈 frontmatter는 빈 객체, 필드 매핑이 아닌 YAML·종료 구분자 누락·파싱/읽기 실패는 Note별 `error`로 표시한다. 오류를 숨기거나 원문을 고치지 않는다. 파서 예외 원문은 속성 값을 노출할 수 있어 응답에 싣지 않는다. 날짜는 응답에서 ISO 문자열로 변환한다.
- 필드 목록은 모든 Note의 frontmatter 최상위 키에서 모은다. 필터는 한 필드에 한 조건을 적용한다. 포함은 대소문자 구분 없이, 같음은 표시 문자열을 정확히 비교하며 리스트는 어느 항목이든 맞으면 포함한다. 존재는 값이 null이어도 키가 있으면 참이다. 중첩 객체는 JSON 문자열로 표시하며 중첩 필드 탐색은 지원하지 않는다.
- 숫자는 숫자 크기로, 다른 값은 표시 문자열로 정렬한다. null/누락 값은 양방향 모두 뒤에 둔다. 기본 순서와 같은 값의 순서는 경로순이다. 그룹은 리스트의 각 값에 표시하되 동일 그룹 안에서는 중복하지 않는다. null/누락/빈 리스트는 `값 없음` 그룹이다.
- Base 진입과 새로고침 때 파일을 다시 읽는다. 보기 설정은 현재 Base 화면에서만 유지하며 저장하지 않는다. 기존 Note 전환 함수와 저장 flush를 재사용하고, 전환 중에는 Base 행을 잠근다. 좁은 화면에서는 내비를 줄바꿈하고 표 컨테이너만 가로로 스크롤한다.

### Phase 5 구현 세부 정책

- **API 계약을 먼저 정하고, 백엔드(5-A)와 화면(5-B)을 병렬로 구현했다.** 계약은 다음 세 가지다.
  - `GET /api/knowledge-updates`
  - `GET /api/knowledge-updates/{id}`
  - `POST /api/knowledge-updates/{id}/undo`

  응답 형태와 409 충돌 형식(`detail.conflicts[].reason = modified|missing`)도 함께 정했다. 두 작업이 서로를 기다리지 않게 하기 위해서다. 병합 후 실제 백엔드와 연결해 확인했다.
- **Undo 실패 코드는 다음과 같다.** 계약에 없던 실패 코드는 구현 중에 정했다.
  - applied가 아닌 기록: 400
  - 다른 Workspace의 기록: 404
  - 충돌: 409
  - 파일 쓰기 실패: 500. 이미 되돌린 파일을 AI 반영 후 내용으로 복구하고, 상태는 applied로 둔다.
  - DB 준비 실패: 503
- **재색인 실패는 Undo 실패로 보지 않는다.** Markdown 복원이 끝났으면 200과 `reindex_error`로 알리고, 해당 Note는 stale로 표시한다. 원본이 진짜 데이터이고 색인은 다시 만들 수 있는 파생 데이터라서다.
- **Undo 전에 Notes 화면의 예약 저장을 멈추고, Undo가 끝나면 다시 켠다.** 열린 Note가 복원되면 다시 읽고, 삭제되면 닫는다. 저장되지 않은 초안이 있으면 덮어쓰지 않고 경고하며, 자동 저장을 오류 상태로 멈춘다. 그대로 두면 예약 저장이 복원·삭제된 파일을 다시 덮어쓸 수 있기 때문이다.
- **Diff 화면 규칙**
  - 바뀌지 않은 구간이 8줄을 넘으면 접고, 변경 앞뒤 3줄만 남긴다.
  - `+`/`-` 기호와 배경색을 함께 써서, 색을 구분하기 어려워도 읽을 수 있게 한다.
  - Undo 확인은 `window.confirm` 하나로 한다.
