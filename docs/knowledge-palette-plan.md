# 지식 팔레트

## 1. 제품 정의

지식 팔레트는 사용자가 LLM과 대화하며 생긴 **생각, 질문, 통찰, 새롭게 이해한 지식**을 자동으로 추출하고, 기존 지식과 비교해 Markdown 기반 개인 지식베이스에 축적하는 로컬 우선 개인 지식관리 앱이다.

핵심은 대화 자체를 보관하는 것이 아니다.

> 대화를 통해 달라진 사용자의 지식 상태를 정리해서 남긴다.

따라서 단순한 AI 채팅 앱도 아니고, 문서 RAG 앱도 아니며, AI가 붙은 Obsidian을 만드는 것도 목표가 아니다.

지식 팔레트의 핵심은 다음 흐름이다.

```text
자료 / 기존 지식
       ↓
   사용자 ↔ LLM
       ↓
새로운 생각 / 질문 / 이해
       ↓
기존 Knowledge Base와 비교
       ↓
CREATE / UPDATE / LINK / NOOP
       ↓
Markdown 지식베이스 갱신
```

---

## 2. 해결하려는 문제

LLM을 사용해 공부하거나 설계할 때 실제 지식은 대화 중에 만들어진다.

하지만 현재 방식에서는:

```text
질문
→ 설명을 들음
→ 추가 질문
→ 이해
→ 판단
→ 대화 종료
```

까지는 자연스럽지만, 이후 다시 직접

```text
Obsidian 열기
→ 관련 노트 찾기
→ 내용 정리
→ 새 노트 작성
→ 링크 연결
```

을 해야 한다.

결국 중요한 생각 대부분은 채팅 기록 안에 묻힌다.

반대로 모든 대화를 자동 요약해서 저장하면 Knowledge Base가 필요 없는 정보로 빠르게 오염된다.

지식 팔레트는 이 사이를 해결한다.

> 모든 대화를 저장하지 않고, 앞으로 다시 찾거나 발전시킬 가치가 있는 지식만 기존 지식과 통합한다.

---

## 3. Source와 Note

지식 팔레트에서는 Source와 Note를 명확하게 구분한다.

### Source

외부에서 들어온 원본 정보.

예:

- PDF
- 강의 자료
- 논문
- Markdown 문서
- 향후 웹 문서 등

Source는 **근거**이지 사용자의 지식 자체가 아니다.

### Note

Source를 읽거나 LLM과 대화하면서 사용자가 이해하고 생각하게 된 내용.

예:

```text
Source:
MMR은 relevance와 diversity를 고려해 결과를 선택한다.

Note:
MMR은 제텔카스텐에서 단순 검색 정확도를 높이는 것보다
비슷하지만 서로 다른 노트를 발견하게 하는 데 더 가치가 있을 수 있다.
```

원본 내용을 자동으로 노트 수백 개로 변환하는 방식은 지양한다.

---

## 4. 무엇을 저장하는가

가장 우선적으로 저장할 대상은 다음과 같다.

### 생각

사용자가 새롭게 내린 판단이나 해석.

> Spring을 사용하는 것보다 Python AI 생태계를 직접 활용하는 편이 지식 팔레트에는 적합하다.

### 통찰

기존에 따로 존재하던 지식 사이에서 발견한 연결.

> MMR의 다양성 확보가 제텔카스텐의 탐색 문제를 보완할 수 있다.

### 질문

아직 답이 없더라도 이후 계속 생각할 가치가 있는 질문.

> Chat과 Note가 모두 1급 작업 공간이라면 둘 사이의 UX는 어떻게 구성해야 하는가?

### 이해한 일반 지식

사용자가 몰랐고, 이후 다시 사용할 가치가 충분한 일반적인 지식.

단, 단순히 새롭게 알았다는 이유만으로 저장하지 않는다.

```text
저장 가능:
MMR이 relevance와 diversity를 함께 최적화하는 원리

보통 저장하지 않음:
현재 Git 브랜치 이름을 출력하는 명령어
```

판단 기준은 엄밀한 카테고리보다 다음 질문에 가깝다.

> 앞으로 다시 찾거나, 다른 생각과 연결하거나, 더 발전시킬 가치가 있는가?

## 5. Knowledge Delta

대화를 Knowledge Base에 그대로 넣지 않는다.

대화에서 기존 Knowledge Base 대비 새롭게 생긴 변화만 추출한다.

이를 Knowledge Delta라고 한다.

```text
CREATE
기존에 없는 지식을 새 Note로 생성

UPDATE
기존 Note에 새 생각이나 이해를 추가

LINK
기존 Note들 사이에 새 연결을 추가

NOOP
저장할 필요가 없거나 이미 충분히 존재
```

기존 Note를 공격적으로 다시 쓰는 것보다는 초기에는 **기존 내용을 보존하며 덧붙이는 방식**을 우선한다.

---

## 6. 자동화 정책

Knowledge Delta는 자동으로 Knowledge Base에 반영한다.

사용자에게 매번

> 저장할까요?

라고 묻지 않는다.

대신 모든 자동 변경은 기록하고 되돌릴 수 있어야 한다.

```text
이번 대화에서

+ 새 Note 1
~ Note 보강 2
↔ Link 추가 1

[변경 내용] [Undo]
```

핵심 UX는:

> 승인 후 자동화가 아니라 자동화 후 필요할 때 Undo

이다.

## 7. Chat과 Note의 관계

Chat이 주요 입력 인터페이스이기는 하지만 Note를 작은 보조 패널로 취급하지 않는다.

둘의 역할은 다음과 같다.

```text
Chat
지식이 만들어지는 작업 공간

Note
지식이 정착하고 발전하는 작업 공간
```

따라서 UI도 항상

```text
왼쪽 사이드바 + 가운데 Chat + 오른쪽 Note
```

형태로 고정하지 않는다.

Chat을 크게 보고 싶을 때는 Chat 전체 화면을 사용하고, Note를 작성하거나 탐색할 때는 Note 전체 화면을 사용한다.

둘을 동시에 볼 필요가 있을 때만 Split View를 사용한다.

## 8. 제품 원칙

### Markdown이 진짜 데이터다

Note의 원본은 Markdown 파일이다.

검색 DB나 Vector DB가 깨져도 Markdown만 있으면 Knowledge Base는 남아 있어야 한다.

### 검색 인덱스는 파생 데이터다

embedding, chunk, 검색 인덱스 등은 필요하면 다시 만들 수 있어야 한다.

### Source는 임의로 변경하지 않는다

앱은 Source 원본을 읽고 색인하지만 사용자의 원본 자료를 마음대로 수정하거나 이동하지 않는다.

### 쓰기 전에 검색한다

새 Note를 만들기 전에 기존 Note를 먼저 검색한다.

중복 Note 생성을 줄이고 기존 생각을 발전시키기 위해서다.

### AI 변경은 되돌릴 수 있다

AI 자동화가 강할수록 Undo가 더 중요하다.

---

## 9. 기존 PKM과의 관계

Obsidian 자체를 재구현하지 않는다.

다만 기존 Markdown 생태계와 최소한의 호환성을 유지한다.

필수 호환 대상:

```text
Markdown
[[wikilink]]
YAML frontmatter
```

지식 팔레트에서 만든 Vault를 일반적인 Markdown 도구나 Obsidian으로 열어도 기본적인 내용과 연결 구조가 유지되는 것을 목표로 한다.

## 10. 제품의 핵심 성공 경험

예를 들어 사용자가 다음과 같은 대화를 한다.

```text
사용자:
MMR을 제텔카스텐 검색에 써먹을 수 있을까?

...

사용자:
그러면 검색 정확도보다
예상하지 못했던 관련 지식을 발견하는 데
더 의미가 있을 수도 있겠네.
```

지식 팔레트는 자동으로 기존 Knowledge Base를 확인한다.

관련 Note:

```text
[[제텔카스텐의 검색 문제]]
```

가 있다면 새로운 Note를 만들거나 기존 Note를 보강한다.

```markdown
# MMR을 이용한 지식 탐색

MMR은 의미적으로 관련된 결과만 반복적으로 가져오는 것을 줄이고
관련성을 유지하면서 서로 다른 내용을 함께 가져올 수 있다.

개인 지식관리에서는 단순 검색 정확도보다
예상하지 못했던 연결을 발견하는 용도로 더 가치가 있을 수 있다.

관련: [[제텔카스텐의 검색 문제]]
```

며칠 뒤 사용자가

> 제텔카스텐에서 AI를 어디에 써야 하지?

라고 물어보면 이 Note가 다시 검색된다.

사용자는 과거 어느 대화에서 이 생각을 했는지 기억할 필요가 없다.

이 경험이 지식 팔레트의 핵심이다.
